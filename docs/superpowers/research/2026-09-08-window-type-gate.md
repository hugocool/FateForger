# How much of `promote_kind`'s gate transfers to minting a window type?

Research for [#386](https://github.com/hugocool/FateForger/issues/386), a child of map
[#382](https://github.com/hugocool/FateForger/issues/382). Read-only: code and docs, no store
was opened. This produces findings, not a design — every "would" below is a candidate for the
decision ticket to accept or reject, not a decision.

## The question

[#382](https://github.com/hugocool/FateForger/issues/382)'s Decisions-so-far record that
*"minting a new window type is gated, the way `memory_promote_kind` already gates minting an
enforceable kind"*. A window type is a named period — sprint, quarter, season — whose live
instance supplies a rule's boundary. It has no anchor. `enforceable_kinds` has an `anchor_uid`
column. So: how much of the precedent actually transfers, and what is the honest analogue of
its post-check?

The short answer, up front:

- **The ordering discipline transfers almost entirely** — it is about minting an identity into
  an append-only log, and none of its four moving parts depends on kinds being anchored.
- **The anchor mismatch is smaller than #386 assumes.** `EnforceableKind.anchor_uid` is written
  once and read by nothing. It is not load-bearing for kinds either.
- **The real mismatch is elsewhere, and it is structural**: the whole ordering exists because a
  kind row carries *no user content the rule does not already state*. A window type row carries
  a length and a phase — standing facts no rule states. "There is no moment at which a kind row
  exists that no rule states" has no clean analogue, because the window row is not stated by the
  rule at all.
- **#140's gate does not govern this.** Every stage 0–5 presupposes a *proposal about the anchor
  taxonomy* generated by the system. A window type is a flat registry entry the user asserts.
  Stage 6 — user confirmation, the only stage that may authorise — is the whole of what applies.
  That is categorically simpler, and it is simpler for the reason #386 suspected.
- **There is an honest post-check, and there are two of them, doing different jobs.** One is the
  direct analogue (reproject and check the rule now names the type); it is *weaker* here than
  for kinds and the repo has measured why. The other has no counterpart in `promote_kind` at
  all: a well-formedness check on the type's own instance arithmetic, which is the only part a
  rule cannot vouch for.

## What `promote_kind` actually does

`MemoryService.promote_kind` (`src/memory/service.py:208-291`), its docstring at
`src/memory/service.py:216-243`, and the design it implements
(`docs/superpowers/specs/2026-09-04-required-blocks-design.md:89-114`, decisions 6–7 at
`:30-39`). In order:

1. **Shape-validate the slug and refuse a duplicate** — `src/memory/service.py:244-246`, with
   `validate_slug` at `src/memory/kind_store.py:39-52` and `DuplicateKind` at
   `src/memory/kind_store.py:24-36`. The validator's own docstring is explicit that it decides
   nothing about meaning: it is a shape check on an identifier the system mints.
2. **Resolve the anchor name through the judge** — `src/memory/service.py:248-250`, preferring
   an existing anchor over a near-duplicate.
3. **Store the rule first**, through the ordinary `observe` path, under the deterministic write
   key `promotion-{slug}` — `src/memory/service.py:252-258`. A suppressed rule aborts the
   promotion (`src/memory/service.py:259-263`).
4. **Register the kind second** — `src/memory/service.py:265-272`.
5. **Post-check by re-derivation**: `reproject(uid=…, apply=True)` on that one constraint with
   the new slug now among the offered kinds, then read it back and require
   `constraint.requires_block == slug` — `src/memory/service.py:273-281`. On failure the kind
   row is deleted (`src/memory/service.py:282-284`, via `EnforceableKindStore.remove` at
   `src/memory/kind_store.py:122-127`) and the caller is told. **The rule stays**, because L1 is
   append-only (I2). Asserted at `tests/memory/test_requires_block.py:133-155`.

The table it writes is `_V4` at `src/memory/migrations.py:103-115`, columns pinned at
`src/memory/migrations.py:143-146`.

Two supporting mechanisms that are part of the gate even though they sit outside the function:

- **The returned slug is verified against the registry before it is ever stored** —
  `src/memory/prompts.py:433-441` raises `UnknownKind` on anything the judge invented, and the
  empty-registry case short-circuits without asking (`src/memory/prompts.py:420-424`). This is
  the closed-choice discipline: the model *picks from* a minted vocabulary, it never extends it.
- **The write key is a trust boundary.** `promotion-{slug}` is not a minted-shaped uid; the MCP
  tool rejects caller-supplied keys that are not (`src/memory/mcp_server.py:162-174`,
  `is_minted_uid` at `src/memory/identity.py:22-39`), and in-process callers are exempt
  precisely because `promote_kind` derives its key from an already-validated slug.

## What transfers

These are properties of **minting an identity into an append-only log**. None of them mentions
anchors, blocks, or days.

**1. The user authorises; `observe` never mints.** `src/memory/service.py:218-220` and the tool
docstring at `src/memory/mcp_server.py:253-255` ("ask the user first: this is a promotion, the
one irreversible write in this design"). The migration comment says the same thing as the
reason the identity is minted rather than paraphrased —
`src/memory/migrations.py:96-98`. This is I3, and it is the entire content of #382's decision.
It transfers unchanged.

**2. Shape validation over content validation.** A window-type name is an identifier the system
mints, so a `validate_slug`-shaped check on it (`src/memory/kind_store.py:39-52`) is inside
`CLAUDE.md`'s exemption and a check on what the *word means* is not. Transfers unchanged.

**3. Refuse a duplicate rather than overwrite.** `src/memory/kind_store.py:24-36`, `:93-96`.
A registry whose rows are never overwritten is what lets a stored reference to a name stay
meaningful. Transfers unchanged, and matters more for windows than for kinds: a kind slug is
referenced by a derived field that `reproject` can re-derive, while a window type's length and
phase are referenced by *arithmetic*, so silently redefining `sprint` moves every attached
rule's boundary at once with nothing to re-derive from.

**4. A deterministic write key so a retry finishes rather than restates.**
`src/memory/service.py:230-233` and `:257`; proven at
`tests/memory/test_requires_block.py:100-130` — the retry adopts the orphan observation rather
than appending a second copy. Transfers unchanged, and the known open hazard transfers with it:
*same key, different payload* is asserted rather than fixed, first payload wins
(`docs/superpowers/specs/2026-08-16-kg-memory-server-design.md:777-787`). For a window type the
divergent payload would be a *number* (a length), not prose, which makes the hazard sharper
rather than milder — see open questions.

**5. Register last, so no row exists that nothing justifies.**
`src/memory/service.py:222-228` names the two failures the earlier order had: a concurrent
`observe` offered a slug about to be rolled back, and a compensating delete as the only thing
between the store and an unjustified row. The first is guarded at
`tests/memory/test_requires_block.py:158+`. **The mechanism transfers; its premise does not** —
see below.

**6. A closed-choice judgement, verified against the registry.**
`src/memory/prompts.py:433-441`, protocol at `src/memory/judge.py:219-221`, called in the
ingest gather at `src/memory/ingest.py:120` and carried by reprojection at
`src/memory/reprojection.py:450`. Whatever types a rule's lifetime must pick a window type from
the registry's current names and be rejected if it invents one. Transfers unchanged, and #383's
point 3 already assumes it.

## What does not transfer, and why

### The anchor column is not the mismatch — it has no reader

`enforceable_kinds.anchor_uid` (`src/memory/migrations.py:106`,
`src/memory/kind_store.py:57`) is written at promotion (`src/memory/service.py:268`) and read
back by the row mapper (`src/memory/kind_store.py:133`) into `PromoteOutcome`
(`src/memory/service.py:43`, `:287`). **Nothing else in the repo reads it.** Every consumer of
the registry goes through `slugs()` — ingest (`src/memory/service.py:137`), reprojection
(`:169`), the `kinds()` surface (`:206`), split (`:314`) — and the read path attaches anchors
from `constraint_anchors`, not from the kind row (`src/memory/read_api.py:221-222`).

So the column is documentation of a join the design named (`…design.md:39`: *"the registry row
is the join between slug and anchor"*) and that nothing has yet needed. **#386's first stated
mismatch is real on the table shape and inert in behaviour**: a window-type registry simply
omits it, and nothing that works today stops working. This does not make the transfer question
easier — it moves it.

### The premise of the ordering does not hold: the row carries facts no rule states

This is the finding that matters.

The ordering works for kinds because a kind row is **wholly justified by the rule**. Its
columns are the slug, an anchor derived by judgement from the promotion call, the uid of the
rule observation, and a timestamp (`src/memory/migrations.py:104-109`). There is nothing in the
row a user asserted that the rule text does not assert. That is why "no moment at which a kind
row exists that no rule states" is a coherent goal, and why deleting the row on a failed
post-check loses nothing: the user's statement survives in L1.

A window type record, per [#384](https://github.com/hugocool/FateForger/issues/384)'s point 1,
holds *a length and a phase anchor date* — how long your sprint is and when the live one
started. Those are standing facts about the user's life. They are not stated by the rule that
happens to be scoped to the sprint; they come from a different statement
(*"my sprints are two weeks"*), possibly from a different session, possibly typed into a panel.

Three consequences:

- **"Rule-first" needs re-reading.** The correct analogue is not "store the scoped rule, then
  register the type"; it is "store *the statement that defines the type* first, then register
  the type" — and the scoped rule may be a third thing entirely. Whether those are one
  interaction or two is a decision ticket question, not a transfer.
- **Deleting the row on a failed post-check is no longer free.** For kinds the rollback
  discards derived data. For windows it discards *asserted* data — a length and a start date
  that nothing else in the store holds in that form, and that cannot be re-derived without
  another sampling call. `promote_kind`'s "the rule stays, the row goes" asymmetry
  (`src/memory/service.py:240-242`) does not reproduce.
- **The mint is not one kind of write.** `promote_kind` takes three inputs and every one of
  them goes through judgement or shape validation: `slug` (shape), `anchor_name` (judged),
  `rule_text` (judged). A window mint additionally carries *numbers the user asserted and no
  model may touch*. That is a configuration write wearing a vocabulary write's clothes, and the
  precedent has no example of it.

### #140's gate does not govern a window type at all

The verdict procedure
(`docs/superpowers/specs/2026-08-16-kg-memory-server-design.md:181-200`) is six checks, and it
is worth naming why each is inapplicable rather than asserting the conclusion:

| stage | check | on a window type |
|---|---|---|
| 0 | diff-size bound over categorical fields | nothing is proposed statistically; there is no diff to size until a rule attaches |
| 1 | **lattice legality** — closure, siblings pairwise disjoint and unioning to the parent | **vacuous.** A window type has no parent and no siblings. It is a flat registry row like `enforceable_kinds`, not a node in the anchor taxonomy |
| 2 | minimum support of 2 on the repair | there is no repair; nothing is being corrected |
| 3 | deletion brake `n > s/e` | nothing is being deleted |
| 4 | **OntoClean rigidity/identity** | **would misfire.** The check exists to reject a *role* posing as a kind (the spec's example: `commute` as a parent of `cycling`, `…design.md:165-166`). A period is anti-rigid *by construction* — "sprint" is a phase, and in OntoClean's own vocabulary phases are anti-rigid and supply no identity criterion. Run as written, this stage rejects every window type, correctly by its own lights and uselessly for this purpose |
| 5 | leave-one-out influence replay | measures flooding by re-running the planner with a constraint removed. Minting a type removes and adds no constraint; the replay diff is empty by construction |
| 6 | **user confirmation** | the only stage that may authorise (`…design.md:197-200`), and the only one that applies |

The reason all of this collapses is I6 read in the right direction: *"promotion by structure,
rejection by statistics; statistics may veto, they may never authorise"*
(`…design.md:87-88`). Stages 0–5 are a **sieve over a proposal the system generated**. #133's
IB3/BBNR shape is the same: IB3's accept / **wait** / retract exists because instance-based
learning has to judge items *nobody confirmed*, and BBNR's liability set exists to attribute
blame for misclassifications *the system made*. Neither has an input when the user states the
type in their own words and confirms it.

**So the answer to #386's crux is: categorically simpler, and for exactly the reason the ticket
proposed.** A window type is not a taxonomy change. It is a vocabulary row the user asserts, and
the gate that governs it is I3's — *only an explicit promotion mints an identity, and `observe`
never does* — not #140's.

Two caveats worth carrying into the decision ticket rather than dropping:

- **The third state does not disappear; it moves.** #140's governing pattern is that a system
  with only keep/retract is one mislabelled observation from a bad permanent edit
  (`…design.md:315-317`). `promote_kind` itself has exactly two states: the post-check passes,
  or the row is deleted (`src/memory/service.py:273-284`). That is defensible for kinds because
  a human is in the loop at that instant and can restate. But for windows the third state
  reappears immediately downstream — a *slipped* instance (#384's point 3) and a *dormant*
  rule (#385) are both "undecided", not "wrong". If a window gate is copied wholesale it will
  inherit the two-state shape into a domain that has a genuine undecided.
- **`Reliability` already encodes the third state and is unwired** (`src/memory/models.py:46-51`
  — *"Three values, not two. Silence is not evidence."*). #387 owns what sets it. A window-type
  gate that wants an "asked and not yet answered" state should not invent a second one.

## What the post-check would be

`promote_kind`'s post-check does two jobs at once, and separating them is the whole of this
section.

**Job A — liveness.** *Nothing would ever require a block of this kind*
(`src/memory/service.py:239-241`). A kind nobody names is dead vocabulary that a future
extraction will nonetheless be offered.

**Job B — round-trip provability of the vocabulary.** Registering last means the rule was judged
before the kind existed (`src/memory/service.py:235-238`), so the reproject both *applies* the
new word and *tests whether the judge can key off it*. This is the more valuable half and the
docstring does not name it.

### The direct analogue exists

Mint `sprint`; store (or already hold) the rule scoped to it; `reproject` that one constraint
with `sprint` now among the offered window types; require that the lifetime judgement
(#383's field) now references `sprint`. If it does not, the word is unusable by the judge and
the type would sit in the registry unreferenced.

Mechanically this is available today: reprojection already carries the closed-choice registry
into `_judge_all` (`src/memory/reprojection.py:450`), and #383's point 3 already commits the
lifetime field to being judged into a system-minted vocabulary.

### It is weaker here than it is for kinds, and the repo has measured why

For `requires_block` the judgement is near-deterministic in the class the noise-floor work
measured (categoricals at 0–1.4%,
`docs/superpowers/specs/2026-08-16-kg-memory-server-design.md:212-224` and
`docs/superpowers/research/2026-08-20-sampler-noise-floor.md`). A single draw is a fair test.

The lifetime vocabulary is **the one categorical this project has caught behaving like a coin
flip.** `CLAUDE.md` records it, and the test is still in the tree:
`test_a_sprint_scoped_cap_is_project_class` (`tests/memory/test_eval_extraction.py:207-216`)
passed on its first run, and nine resamples of the identical text returned `permanent` eight
times. The cause named in `CLAUDE.md` is that the prompt gave the model nothing to key off
between `project` and `permanent` — which is precisely the discrimination a window type asks
for, on the same sentence, from the same family of rule. `DecayClass`'s own docstring flags the
vocabulary as provisional and hand-authored (`src/memory/models.py:74-82`).

So: **an n=1 post-check on a window type is a materially weaker guarantee than the same n=1
post-check on a kind, and the difference is measured, not speculative.** Whether the check
resamples (and at what n, and what a split verdict means) is a decision-ticket question. Note
that `promote_kind`'s retry path makes resampling almost free — the same slug and rule text
adopt the stored observation rather than restating it
(`tests/memory/test_requires_block.py:100-130`) — but a retry is currently a *retry after
failure*, not a deliberate n-draw, and `CLAUDE.md`'s eval discipline says a judgement validated
by one passing call has not been validated.

### The part with no analogue, and the part `promote_kind` has no counterpart for

**No analogue:** liveness (Job A) is not obviously a failure for a window type. A kind exists
*only* to be required by a rule, so an unreferenced kind is inert. A window type is a fact about
the user's calendar life that stays true whether or not a rule currently hangs on it — a sprint
cadence outlives the rules scoped to any one sprint, and #382's dormancy decision explicitly
keeps rules parked across instance boundaries. **Deleting a window type because no rule
currently references it would delete a true standing fact.** That is a genuine break in the
precedent, and it is the direct consequence of the row carrying user-asserted content.

**No counterpart in `promote_kind`:** a window type has a check kinds do not need at all. Its
whole purpose is to yield instance boundaries by arithmetic at read time, and that arithmetic
can be *ill-formed* independently of any rule — a zero or negative length, a phase date that
makes no instance contain today, an override set (#384's point 3) that leaves a gap or an
overlap between consecutive instances. This is the one place a structural check in #140's sense
genuinely applies, and it is the closest thing here to stage 1's argument: overlapping or
gapping instances are *not* a structure the user disagrees with, they are a structure the read
path silently answers wrongly from, which is the spec's stated reason lattice legality is the
one non-overridable stage (`…design.md:271-276`). Prior art gives this check a name — see
below.

**A candidate shape, for the decision ticket to accept or reject:** the window-type post-check
is two assertions, not one — *(i)* the instance function is total and non-overlapping over the
horizon it will be asked about (structural, free, non-overridable, no model); and *(ii)* the
judge can attach a rule to the new name (round-trip, one or more model calls, and the failure
means "this word is not usable", which may warrant asking the user for a better one rather than
silently deleting a fact they stated).

## Invariant I1 — what would violate it if copied

I1 is scoped narrowly (`…design.md:73-80`) and enforced by an AST test that is stricter than it
first looks: `tests/memory/test_read_api.py:96-129` is an **import allow-list**, currently
`{__future__, datetime, memory.anchor_store, memory.constraint, memory.constraint_store,
memory.models}`, plus an assertion that `read_api` contains **no async function and no await**
at all. `tests/memory/test_decay_read.py:75-99` does the same for the decay read.

Four things in the promote path would violate it if copied naively:

1. **Name resolution.** `promote_kind` resolves `anchor_name` through the judge
   (`src/memory/service.py:249`), and `resolve_anchor_names` is a separate host-called sampling
   step precisely so the read path never does it (`src/memory/service.py:190-202`). Turning the
   words *"this sprint"* into a window-type id is the same judgement, and it must happen at
   write/projection time with the **id** stored. The read path may only take an id and do
   arithmetic — the exact pattern `get_active_constraints` already uses for anchors
   (`src/memory/read_api.py:22`, docstring at `src/memory/service.py:324-331`).
2. **Reaching the registry from `read_api`.** Deciding which instance is live needs the type's
   length and phase, which live in a new store module. Importing it from `read_api` fails the
   allow-list until it is added — and it may only be added if that module is a pure SQLite
   module in the shape of `anchor_store` (the allow-list's own comment,
   `tests/memory/test_read_api.py:115`, admits `memory.anchor_store` on exactly that ground).
   The guard working as designed is a feature; it is worth knowing before the shape is chosen.
3. **Anything async.** Instance arithmetic must be synchronous. `read_api` is asserted to
   contain no `async def` and no `await` (`tests/memory/test_read_api.py:127-129`), which rules
   out a lazily-sampled instance lookup even behind a cache.
4. **Slip correction at read time.** #384's point 3 already names this; restating it as an I1
   consequence: a slipped instance must be corrected by *stored data* (an override table, RFC
   5545's `RECURRENCE-ID`/`EXDATE` shape) written on the write path, never by a model call
   deciding at read time which boundary "really" applies. A model in that position also breaks
   the weaker guarantee I1 exists to protect — the same day read twice answering differently
   (`src/memory/service.py:194-197`).

Nothing in `promote_kind` itself violates I1: it is a write-path call and samples freely
(anchor resolution, six ingest judgements, one reprojection —
`src/memory/mcp_server.py:268-269`). The risk is entirely in what a window type is *for*, which
is a read-time computation kinds never had.

## Prior art outside the repo — only where it changes the answer

Three citations that change something. Everything else in the neighbourhood
(#140's IB3/BBNR sweep, the belief-revision family) is answered by "the user confirms directly",
above.

- **OntoClean's rigidity meta-property** (Guarino & Welty). Cited by the spec at
  `…design.md:165-166` and stage 4 at `:181-197`. It changes the answer by *ruling itself out*: a
  period is a phase, anti-rigid by construction, so stage 4 would reject every window type on
  correct grounds that have nothing to do with whether the type is a good one. Without this
  note, a decision ticket copying the gate stage-by-stage would read stage 4's rejection as a
  signal.
- **Time granularity in temporal databases** (Bettini, Jajodia & Wang; the same shape underlies
  SQL:2011's application-time periods). A named granularity — business week, academic semester,
  fiscal quarter — is a mapping from an index to sets of time points, and the literature's
  standard well-formedness conditions are exactly monotonicity, non-overlap and coverage. This
  changes the answer at §"the part with no counterpart": the structural check on a window type's
  instance arithmetic is not something this project has to invent, and the conditions to assert
  are named. It also supports the framing that a window type is *declared, not induced* —
  granularities in that literature are always declared.
- **RFC 5545's split between a recurrence rule and its instances** (`RRULE` vs
  `RECURRENCE-ID`/`EXDATE`). Already recorded on #384, restated here only because it is what
  makes the I1 slip-correction constraint satisfiable: per-instance overrides are stored data,
  so the read path stays arithmetic.

For **user-confirmed vocabulary growth** specifically — the actual subject of #386 — there is no
settled external answer better than this repo's own precedent. The nearest neighbours (SKOS
editorial workflows with candidate/approved concept status, terminology-management practice) say
only what `promote_kind` already says: a proposed term is not a term until a human accepts it,
and acceptance is recorded. **The repo's own precedent is the best available**, which is why
this document spends its length on how far it stretches rather than on alternatives.

## Open questions for the decision ticket

1. **Is the window-defining statement the same interaction as the scoped rule?** The whole
   ordering discipline assumes one statement justifies the row. Here there are plausibly two
   (*"my sprints are two weeks, this one started Monday"* and *"cap framing at 15 minutes this
   sprint"*). Which one is stored first, and is the type's own defining statement an observation
   in L1 at all?
2. **What happens to the length and the phase on a failed post-check?** `promote_kind` deletes
   the row and keeps the rule. Deleting a window row discards user-asserted facts. Is the
   failure a delete, a refusal to write, or a row kept in a not-yet-usable state?
3. **Does the post-check resample, and at what n?** The lifetime vocabulary is the one
   categorical measured near a coin flip in this repo
   (`tests/memory/test_eval_extraction.py:207-216`, `CLAUDE.md`). An n=1 check inherits that.
   And what does a split verdict mean — retry, ask for a different name, or accept?
4. **Is liveness a failure at all?** A window type nothing currently references may still be
   true. If liveness is dropped as a criterion, Job A of `promote_kind`'s post-check has no
   analogue and the check becomes only the round-trip plus the arithmetic well-formedness.
5. **Does the well-formedness check have a horizon?** "Total and non-overlapping over the dates
   it will be asked about" needs a bound. Unbounded is not checkable; the planning horizon is a
   candidate.
6. **Same key, different numbers.** The retry key makes a promotion idempotent by name, and the
   store's documented rule is *first payload wins*
   (`…design.md:777-787`). If a second promotion of `sprint` carries a different length, "first
   payload wins" silently discards a correction. For prose that is conservative; for a number
   that drives arithmetic it may be the wrong default. Related to how a *changed* sprint length
   is expressed at all — which is a re-definition, not a mint, and the precedent has no verb for
   it.
7. **Where does the third state live?** Slipped instances and dormant rules are genuinely
   undecided (#384, #385), `Reliability` already has the vocabulary and no writer (#387,
   `src/memory/models.py:46-51`). The gate should not mint a second undecided.
8. **Non-time-derived windows** (#384's point 5, #382's fog). The arithmetic well-formedness
   check is the strongest thing this document proposes and it presupposes a length. A renovation
   has none — so either it is not a window type, or the structural half of the post-check does
   not apply to it, which makes it a different thing wearing the same field.

## Contradictions and sharpenings against #382's Notes and Decisions

Recorded plainly, because the map asked for findings that bear on its own record.

- **#382's decision** — *"minting a new window type is gated, the way `memory_promote_kind`
  already gates minting an enforceable kind"* — **holds on the authorisation half and does not
  hold on the ordering's premise.** The user-asks-first half transfers exactly. "Rule-first, so
  no row exists that no rule states" does not survive a row that carries facts no rule states.
- **#386's stated first mismatch is smaller than it reads.** `anchor_uid` has no reader
  (`src/memory/kind_store.py:133`, `src/memory/service.py:287`, and nothing downstream). The
  table shape does not transfer; nothing behavioural depends on it.
- **#386's second framing is sharpened.** The gate's real content is an ordering *plus two
  post-checks*, one of which (`liveness`) may be wrong for windows and one of which
  (arithmetic well-formedness) `promote_kind` does not have.
- **#382's Decisions cite #133's IB3/BBNR shape as the gate.** `promote_kind` implements neither
  and has the two-state shape #140 names as the defect (`…design.md:315-317`). That is fine for
  kinds — a human is present and the append-only half is retained — but it means "gated the way
  `promote_kind` is gated" and "gated the way #133 decided" are two different gates, and #382's
  Decisions currently read as though they were one.
